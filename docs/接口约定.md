# 核心接口约定

所有错误统一返回：

```json
{"detail": "可直接展示给用户的原因"}
```

当前开发阶段用 `X-Role`、`X-Subject-ID` 请求头模拟登录用户。生产配置不会接受这种身份来源；成员 3 应替换 `app/auth_contract.py`，并保持 `CurrentUser(role, subject_id)` 结构不变。

## 学生方案

- `GET /semesters/{semester_id}/schedule`：读取当前用户的草稿、正式主选、正式备选和版本。
- `PUT /semesters/{semester_id}/schedule/draft`：保存完整草稿，不占名额。
- `POST /semesters/{semester_id}/schedule/submit`：把当前草稿整体提交。
- `DELETE /semesters/{semester_id}/schedule/offerings/{offering_id}`：单独退课。
- `DELETE /semesters/{semester_id}/schedule`：确认后删除整份方案。

保存草稿请求示例：

```json
{
  "expected_version": 1,
  "choices": [
    {"offering_id": 11, "kind": "primary"},
    {"offering_id": 12, "kind": "primary"},
    {"offering_id": 13, "kind": "primary"},
    {"offering_id": 14, "kind": "primary"},
    {"offering_id": 15, "kind": "alternate", "alternate_priority": 1},
    {"offering_id": 16, "kind": "alternate", "alternate_priority": 2}
  ]
}
```

提交、退课和删除请求只需当前版本：

```json
{"expected_version": 2}
```

成功后响应给出新 `version`。页面必须保存新版本；收到 `409` 和“重新载入”提示时重新获取方案。

## 教务关闭

- `POST /registrar/semesters/{semester_id}/close`

响应包含取消班次 ID 和本次创建的账单任务数。关闭成功不代表外部计费已收到；成员 2 应单独展示 `BillingJob.status`，成员 4 负责发送状态接口与重试器。

## 集成约束

- 成员 2：不要根据页面剩余名额自行判定提交成功，以后端结果为准。
- 成员 3：每次请求都检查账号当前状态；不要信任请求体中的学生 ID。
- 成员 4：成绩通过值为 A-D；先修检查只读取当前有效成绩。账单发送使用任务中的金额和 JSON 快照，不重新查询并计算。
- 所有修改学期/班次的业务入口遵守“学期 -> 业务主体 -> 班次 ID 升序”的锁顺序。
