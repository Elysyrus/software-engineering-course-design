## BUG-01 账单任务时间舍入到整秒，关闭后立即派发可能漏发

**发现方式**：执行接口验收时，关闭选课后立刻调用“立即派发到期账单”（TC-BIL-01）。6 次完整执行中有 1 次返回 `dispatched: 0`，12 条账单都没有被取出。

**复现方法**：关闭选课后 0.5 秒内调用 `POST /api/v1/registrar/billing/dispatch`。现象是偶发的，取决于关闭时刻的小数秒是否大于 0.5。

**实际结果**：

```json
{"dispatched": 0, "sent": 0, "failed": 0, "abandoned": 0, "retrying": 0, "results": []}
```

**预期结果**：关闭后立即派发，应取出全部 12 条到期账单。

**原因**：`billing_jobs.next_attempt_at` 是 `DateTime(timezone=True)`，在 MySQL 中建成 `DATETIME`，不保存小数秒，而且四舍五入。实测 `13:18:14.7` 存成 `13:18:15`，`13:18:14.3` 存成 `13:18:14`。关闭事务写入的时间若被进位到下一秒，紧接着派发时比较 `next_attempt_at <= 当前时间` 不成立，任务暂时不被取出。

**影响**：低。后台重试进程每 5 秒轮询一次，下一轮会正常发送，账单不会丢失。但教务在关闭后马上点“立即派发”时，可能看到“本次派发 0 条”，容易误以为出错。另外 12 个时间列也有同样的精度损失。

**修复**：

- `app/models.py`：新增 `Timestamp` 类型，MySQL 下为 `DATETIME(6)`（保留微秒），其他数据库不变；全部 13 个时间列改用它。
- 新增迁移 `migrations/versions/fsp20261009_mysql_microsecond_timestamps.py`：把已有 MySQL 库的 13 个时间列改为 `DATETIME(6)`，不改动数据；SQLite 下不做任何操作；支持回退。
- `tests/test_mysql_final.py`：新增回归测试 `test_billing_job_due_immediately_keeps_fractional_seconds`，写入 `.700000` 秒的账单任务，确认读回保留微秒，并且在同一时刻立即派发能取到。

**复测**（2026-10-09，MySQL 8.0.42）：

| --- | --- |
| 新回归测试，修复前的模型 | 不通过：读回的微秒为 0 |
| 新回归测试，修复后 | 通过 |
| 在已有演示数据的库上执行迁移 | 13 个时间列全部变为 `datetime(6)`，原有 21 个账号保留 |
