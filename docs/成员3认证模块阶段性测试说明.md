## 2. 测试的共同基础：`conftest.py`

`member3/test/conftest.py` 提供 `db` fixture（夹具）。每个测试开始时：

1. 新建一个 SQLite 内存数据库；
2. 用 `Base.metadata.create_all()` 建立全部表；
3. 把 SQLAlchemy `Session` 交给测试函数；
4. 测试结束后删除表。

因此每个测试的数据彼此隔离。`StaticPool` 让 FastAPI 的 `TestClient` 请求与测试函数使用同一内存数据库连接，测试中的 HTTP 请求才能读到刚创建的账号和会话。

## 3. `assert` 的作用

`assert 条件` 是 Python 的断言：条件为真，测试继续；条件为假，pytest 报告失败，并指出对应行。

例子：

```python
assert response.status_code == 401
assert account.must_change_password is True
assert verify_password("Initial123", account.password_hash) is True
```

这三句分别验证：HTTP 状态码正确、首次改密标记正确、密码哈希能够验证正确密码。测试不是“代码运行不报错”就算通过，而是每个业务结果都要用断言核对。

## 5. `test_auth_unit.py`：认证服务单元测试

这组测试不启动 HTTP 服务，而是直接调用 `app.services.auth` 的函数，因此定位问题快，适合验证单个业务规则。

| 测试 | 测试流程 | 主要断言 |
| --- | --- | --- |
| `test_validate_password_rejects_weak_passwords` | 依次传入过短、全数字、全字母密码。 | 均抛出 `ValueError`。 |
| `test_hash_password_never_stores_plaintext_and_verifies` | 对明文生成哈希，再用正确和错误密码验证。 | 哈希不等于明文；正确密码为 `True`，错误密码为 `False`。 |
| `test_create_account_and_authenticate` | 创建学生与账号，再调用登录认证。 | 密码非明文、账号必须首次改密、正确密码能找到同一账号。 |
| `test_duplicate_login_and_bad_credentials_are_rejected` | 重复创建同一登录编号；再分别用错误密码和不存在账号登录。 | 重复编号为 `409`；两种登录失败均为 `401`，避免账号枚举。 |
| `test_disabled_account_cannot_authenticate` | 创建账号后设为停用，再登录。 | 返回 `403`。 |
| `test_session_resolves_account_and_rejects_expired_session` | 创建有效 Session 后读取账号，再把到期时间改为过去。 | 有效 Session 可解析账号；过期后为 `401`。 |
| `test_change_password_revokes_all_existing_sessions` | 同一账号创建两个 Session，执行改密。 | 首次改密标记变为 `False`、新密码可验证、两个 Session 都有 `revoked_at`。 |
| `test_change_password_failure_preserves_password_and_sessions` | 分别传错误旧密码、弱新密码。 | 原哈希、首次改密标记、Session 撤销状态均不改变。 |
| `test_logout_revokes_session_and_is_idempotent` | 对同一 Session 连续调用两次 `logout()`。 | 第二次安全执行；Session 已撤销，后续解析为 `401`。 |
| `test_validate_csrf_requires_the_matching_session_token` | 依次传正确、缺失、伪造 Token。 | 正确通过；缺失和伪造均为 `403`。 |

## 6. `test_auth_integration.py`：认证与接口集成测试

该文件会建立最小 FastAPI 应用，并将 `get_db` 覆写为测试数据库。它验证的完整链路是：

```text
HTTP Cookie: session_id
  -> current_account()
  -> get_session_account()
  -> CurrentUser(role, subject_id)
  -> require_student / require_teacher / require_registrar
  -> 具体页面或 API
```

| 测试 | 验证内容 |
| --- | --- |
| `test_cookie_session_is_converted_to_current_user` | 有效 `session_id` Cookie 转换为正确的角色和 `subject_id`。 |
| `test_missing_cookie_is_unauthenticated` | 没有 Cookie 时返回 `401` 与“未登录”。 |
| `test_role_guards_allow_only_the_matching_role` | 学生、教师、教务只能通过各自的角色依赖；学生访问教师依赖返回 `403`。 |
| `test_disabling_an_account_blocks_an_existing_cookie` | 登录后停用账号，旧 Cookie 下一次访问立即被拒绝。 |
| `test_disabling_the_linked_student_blocks_an_existing_cookie` | 登录后停用学生档案，即使账号仍存在，旧 Cookie 也被拒绝。 |
| `test_first_login_cannot_use_regular_current_user` | `must_change_password=True` 的账号不能走普通业务身份依赖。 |
| `test_login_change_password_and_logout_routes_require_csrf` | 真实登录设置 HttpOnly Cookie；改密缺 CSRF 为 `403`；正确 CSRF 可改密、重新登录与退出。 |
| `test_page_entries_require_real_login_and_matching_role` | 学生、教师、教务页面必须真实登录且角色匹配。 |
| `test_first_login_can_open_change_password_page_only` | 首次登录账号可打开改密页，但访问学生页面为 `403`。 |
| `test_registrar_can_create_student_and_teacher_via_admin_api` | 教务携带 CSRF 后可创建学生、教师；返回按年份生成的编号。 |
| `test_admin_user_creation_requires_registrar_and_csrf` | 未登录为 `401`；学生即使带 CSRF 也为 `403`；教务缺登录不能读取。 |
| `test_registrar_can_manage_user_lifecycle_via_admin_api` | 教务完成创建、详情、编辑、停用、重置密码、删除的完整生命周期；停用缺 CSRF 返回 `403`。 |

这不是成员 1、4 真实业务接口的回归测试。学生选课与教师成绩的真实业务接口合并后，仍需把上述 Cookie 身份链接入那些接口并补数据权限测试。

## 8. `test_init_script.py`：可执行教务初始化脚本测试

`scripts/init_registrar.py` 的命令行入口较难在测试中直接输入密码，因此测试调用其核心函数 `initialize_registrar()`。

`test_initialize_registrar_script_creates_and_reuses_registrar` 的流程：

1. 第一次传入 `registrar` 与初始密码；
2. 第二次故意传入不同登录编号和密码；
3. 查询数据库；
4. 断言两个调用返回同一账号 ID 和最初的登录编号；
5. 断言最初密码仍能验证，第二次传入的密码不能验证。

它验证了脚本的关键安全规则：重复执行不会创建第二个教务账号，也不会意外覆盖已设置的密码。

## 9. `test_seed_demo_data.py`：演示数据初始化测试

`scripts/seed_demo_data.py` 用于答辩前快速补充测试数据。测试调用 `seed_demo_data()` 两次：

1. 第一次调用应新增 1 个教务、3 名学生、2 名教师、3 门课程；
2. 第二次调用应返回全部为 0，表示没有重复创建；
3. 查询数据库核对三类人员/课程总数；
4. 验证教务密码保持第一次的值；
5. 验证演示学生账号初始密码为 `Initial123`，且必须首次改密。

这验证脚本“只补充缺失记录，不删除、不覆盖已有记录”的幂等行为。

## 10. 已覆盖与未覆盖的验收项

### 已覆盖

- 密码安全、账号不存在与密码错误统一 `401`。
- 停用账号或人员后旧 Session 立即失效。
- 首次登录只能改密或退出。
- 登录 Cookie、CSRF、改密、退出。
- 学生、教师、教务页面入口的角色隔离。
- 教务人员账号的创建、编辑、重置、启停、删除。
- 有历史记录时停用而非删除。
- 事务异常回滚。
- 教务与演示数据初始化的幂等性。

## 11. 当前测试警告

当前通过测试时会看到两类第三方库弃用警告：

- `TestClient` 的“每请求传 Cookie”写法建议改为 `client.cookies.set()`；
- Starlette 推荐新的 `TemplateResponse(request, name, context)` 参数顺序。

它们不改变断言结果，也不影响当前功能；可在代码整理阶段处理。
