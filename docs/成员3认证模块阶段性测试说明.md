## 2. 测试代码如何工作

### 2.1 测试数据库夹具

`conftest.py` 在每个测试开始时用 `Base.metadata.create_all()` 建立一套 SQLite 内存表；结束后删除表。测试之间没有账号、会话或数据残留。`StaticPool` 保证 FastAPI 测试请求和测试函数访问同一个内存数据库连接。

### 2.2 单元测试：认证服务规则

`test_auth_unit.py` 不启动 HTTP 服务，而是直接调用 `app.services.auth` 中的函数。

| 测试 | 验证逻辑 |
| --- | --- |
| `test_validate_password_rejects_weak_passwords` | 密码过短、仅数字、仅字母均被拒绝。 |
| `test_hash_password_never_stores_plaintext_and_verifies` | 数据库存储的不是明文；正确密码可验证，错误密码不能验证。 |
| `test_create_account_and_authenticate` | 创建账号默认要求首次改密，并能用初始密码认证。 |
| `test_duplicate_login_and_bad_credentials_are_rejected` | 重复登录编号返回 409；错误密码返回 401。 |
| `test_disabled_account_cannot_authenticate` | 停用账号无法重新登录，返回 403。 |
| `test_session_resolves_account_and_rejects_expired_session` | 有效会话可找到账号；到期会话返回 401。测试刷新实体，模拟 SQLite 从数据库读取无时区时间的真实路径。 |
| `test_change_password_revokes_all_existing_sessions` | 改密后保存新哈希、取消首次改密标记，并撤销同一账号已有的所有会话。 |
| `test_validate_csrf_requires_the_matching_session_token` | 仅允许与会话中保存值一致的 CSRF Token；缺失或伪造均返回 403。 |

### 2.3 集成测试：Cookie 到角色授权的链路

`test_auth_integration.py` 创建最小 FastAPI 应用，并覆写 `get_db`，使 HTTP 请求使用测试数据库。它验证的链路是：

```text
session_id Cookie
  -> current_user()
  -> get_session_account()
  -> CurrentUser(role, subject_id)
  -> require_student / require_teacher / require_registrar
```

| 测试 | 验证逻辑 |
| --- | --- |
| `test_cookie_session_is_converted_to_current_user` | 有效 Cookie 能返回数据库中的角色和人员主体 ID。 |
| `test_missing_cookie_is_unauthenticated` | 没有 Cookie 时返回 401。 |
| `test_role_guards_allow_only_the_matching_role` | 学生、教师、教务只能通过各自对应的角色依赖；学生访问教师入口返回 403。 |
| `test_disabling_an_account_blocks_an_existing_cookie` | 登录后再停用账号，旧 Cookie 的下一次请求会立即返回 403。 |

## 3. 已发现但尚未覆盖的测试场景

以下项目应在后续迭代中补充。它们按优先级排列。

### 已补齐的高优先级项

1. `logout()` 已测试撤销会话及重复调用幂等；撤销后的会话返回 401。
2. 已覆盖账号不存在与错误密码均返回 401。
3. 已覆盖原密码错误、弱新密码不会修改密码哈希、首次改密标记或会话状态。
4. 认证路由已测试 Cookie 设置、缺失 CSRF 返回 403、正确 CSRF 可改密和退出。

### P1：依赖功能补全后再测试

1. **真实业务路由回归**：现有认证集成测试尚未覆盖成员 1 的选课路由与成员 4 的教师路由。真实登录后，应测试学生能进入自己的选课入口、教师/教务被拒绝；并保留成员 1 的版本冲突和业务返回行为。
2. **真实业务路由中的数据权限**：页面入口已按角色保护；成员 1/4 的业务路由仍需分别验证“当前学生的方案”和“当前教师的班次”归属，不能仅凭角色放行。

### P2：安全性与数据库质量

1. 并发创建相同登录编号：确认数据库唯一约束作为最终保护，并将 `IntegrityError` 转换为统一 409 响应。
2. 会话字段质量：验证会话 ID、CSRF Token 不重复，且有效期为预期时长。
3. Cookie 安全属性：正式路由完成后验证 `HttpOnly`、`SameSite`，以及生产环境下的 `Secure`。
4. 会话清理：验证过期或撤销会话的定期清理任务不会影响有效会话。
5. 密码库异常：覆盖无效/损坏密码哈希的处理，避免 500 错误暴露给客户端。

## 4. 当前实现注意事项

- SQLite 读取 `DateTime` 常为无时区对象。当前 `get_session_account()` 根据读取到的时间是否带时区，选择匹配的 UTC 比较值。生产数据库应统一按 UTC 存储、迁移并验证时间语义。
- 测试使用 `TestClient` 的每请求 Cookie 方式会产生依赖弃用警告；目前不影响测试结果，后续可改为 `client.cookies.set("session_id", value)`。
