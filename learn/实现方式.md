# `learn/` 的实现方式与注意事项

`learn/` 是成员 3 的可运行学习示例，不会被 `app/main.py` 导入，也不会改动当前课程系统的数据库。它把正式项目中还未实现的认证和师生管理规则，先拆成纯 Python 服务函数，便于逐步理解状态变化。

## 1. 采用的结构

```text
页面/HTTP 路由（正式项目待接入）
              ↓
认证函数：auth.py
              ↓
资料管理函数：personnel.py
              ↓
MemoryStore：models.py
```

- `models.py` 用 dataclass 表示 `Account`、`ServerSession`、学生和教师资料。
- `auth.py` 处理密码、登录、会话、当前用户、角色检查、改密、退出和 CSRF。
- `personnel.py` 处理师生资料、编号、创建、查询、修改、停用和删除。
- `MemoryStore` 是字典和集合组成的内存仓库。它使函数可直接运行，但进程结束数据就消失。
- `test_member3_functions.py` 只测学习函数的规则，不调用 FastAPI、Cookie、MySQL 或成员 1/4 的真实业务表。

正式系统要把 `MemoryStore` 换成 SQLAlchemy 查询和数据库事务；业务规则可以保留，存储实现不能直接照搬。

## 2. 登录和权限的实现方式

```text
登录编号 + 密码
      ↓ authenticate_user
Account（账号、角色、主体 ID、启用状态）
      ↓ create_session
ServerSession（随机会话 ID、CSRF 令牌、有效期、撤销时间）
      ↓ get_session_account
CurrentUser(role, subject_id)
      ↓ require_student / require_teacher / require_registrar
成员 1 或成员 4 的业务归属检查
```

密码使用 `pwdlib` 推荐的 Argon2 实现生成哈希。示例中不保存明文密码，也不会自己拼接盐或设计加密算法。

会话 ID 与 CSRF 令牌分别随机生成，职责不同：

| 值 | 作用 | 正式项目的放置方式 |
| --- | --- | --- |
| 会话 ID | 找到服务端保存的登录会话。 | 放入 HttpOnly Cookie；服务器保存会话记录。 |
| CSRF 令牌 | 证明修改请求来自已加载的受信页面。 | 页面读取可提交的令牌，在写请求中附带；服务器与会话记录比较。 |

`get_session_account()` 每次都会重新检查会话是否存在、是否过期或撤销，以及账号与关联师生是否仍启用。这样停用账号后，旧 Cookie 也不能继续访问。

## 3. 三种 ID 必须分清

| 名称 | 示例 | 用途 |
| --- | --- | --- |
| 账号 ID | `Account.id` | 管理登录、密码和会话。 |
| 人员主体 ID | `Student.id`、`Teacher.id` | 供成员 1、4 的业务表关联。 |
| 登录编号 | 学号、教师编号 | 页面输入和展示。 |

`CurrentUser.subject_id` 必须是人员主体 ID：学生时对应 `Student.id`，教师时对应 `Teacher.id`。不能把账号 ID 或学号字符串直接传给成员 1 的选课函数。教务主体 ID 的存储方式尚需在正式设计中确定。

## 4. 资料管理和删除策略

创建学生或教师时，示例先校验资料，再在同一个 `MemoryStore.transaction()` 块中写入人员和账号。它演示的目的是：账号创建失败时，不能留下没有账号的人员资料。

`delete_or_deactivate_student()` 和 `delete_or_deactivate_teacher()` 采用两条分支：

- 没有业务历史：删除人员和账号。
- 有业务历史：保留人员、选课、成绩和账单，只停用账号，并撤销旧会话。

学习示例用 `student_business_records`、`teacher_business_records` 集合人工标记“存在历史”。正式代码必须查询成员 1 的 `Schedule`、`Grade`、`BillingJob`、`Offering`，以及成员 4 后续增加的历史表；不能把示例集合原样复制到应用中。

## 5. 与当前项目接口的衔接

正式认证接入时应替换 `app/auth_contract.py` 内的开发身份头逻辑，但保持：

```python
CurrentUser(role, subject_id)
```

以及已有的学生选课和教务关闭路径不变。认证层只提供可信身份，不能修改成员 1 的 `expected_version`、409 版本冲突、容量检查、选课事务或关闭选课流程。

成员 4 只应复用 `current_user()` 与 `require_teacher()`；教师是否有资格教授课程、是否拥有班次、是否能修改某个学生的成绩，仍由成员 4 的业务函数判断。

成员 2 当前页面使用 `/api/v1/auth/...`、`/api/v1/admin/users...` 和 localStorage 中的假令牌。这些是联调模拟实现，不是已确定的正式认证契约。正式接入需要统一以下内容：

- 后端角色使用 `registrar`，前端可以显示“教务管理员”，但不能把 `admin` 当作可信权限。
- 登录成功后设置 HttpOnly Cookie，页面不再把角色或授权令牌作为权限依据。
- 页面调用真实退出接口，再清理展示状态。
- 所有修改请求同时完成会话认证和 CSRF 检查。
- 认证、权限和校验失败统一返回 `{"detail": "可直接展示给用户的原因"}`。

## 6. 你最需要注意的部分

1. **先认证，再授权，再检查业务归属。** 登录成功不等于可以访问所有接口；教师角色也不能自动修改所有班次成绩。
2. **首次改密需要例外入口。** 改密和退出使用基础会话检查，其他业务接口才阻止 `must_change_password=True` 的账号。
3. **停用必须撤销旧会话。** 只把 `active` 改为 `False` 不够；每次请求都要重新检查状态。
4. **账号 ID 和人员 ID 不可混用。** 停用、重置密码按账号 ID；选课、成绩、班次按学生或教师主体 ID。
5. **密码哈希与会话 ID 都不能返回或写入日志。** 响应只给页面需要的信息。
6. **内存事务不是数据库事务。** `MemoryStore.transaction()` 没有真实并发控制；正式创建编号必须通过数据库唯一约束兜底。
7. **删除前要检查历史。** 软删除的 `Schedule` 也属于历史。教师的授课、成绩变更等关联完成后，要把它们加入检查。
8. **不要从请求体取得当前学生。** 当前身份只能从经过验证的会话转换而来。
9. **不要把成员 2 的模拟 API 当成正式契约。** 认证和人员管理接口的最终字段、Cookie 和状态码要写入 `docs/接口约定.md`。

## 7. 当前示例的边界和下一步

示例已经演示密码哈希、首次改密、会话撤销、CSRF 比较、停用、资料创建及“删除或停用”规则。它尚未实现：数据库表和迁移、FastAPI 路由依赖、Cookie 设置、真实历史查询、并发唯一约束、页面改造和成员 4 的真实业务表联调。

把学习代码接入正式项目时，建议按这个顺序进行：

1. 在 `app/models.py` 和 Alembic 迁移中新增账号、会话及资料字段。
2. 将 `auth.py` 的规则迁移为数据库服务，并在 `app/auth_contract.py` 保持 `CurrentUser` 契约。
3. 实现登录、改密、退出和 CSRF 路由，再补师生管理路由。
4. 替换成员 2 的模拟请求，保留成员 1 已确定的正式业务接口。
5. 增加真实认证、停用旧会话、越权和历史删除的自动化测试。
