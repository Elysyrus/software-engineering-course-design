## 2. 成员 3 的必做功能

### 2.1 账号与会话生命周期

- **[需求-已确认]** 系统不开放自行注册。教务创建学生和教师账号；教务账号通过初始化创建。
- **[需求-已确认]** 系统分配唯一学号或教师编号，并将其作为唯一登录编号；账号登录编号全局唯一。
- **[需求-已确认]** 新账号使用初始密码，首次登录必须修改密码。
- **[需求-授权决定]** 密码只保存安全哈希，使用成熟密码哈希库，不自行设计加密算法。
- **[需求-授权决定]** 使用服务端会话和 HttpOnly Cookie；修改类请求校验 CSRF。
- **[需求-授权决定]** 首次改密前只允许访问改密和退出功能。
- **[需求-授权决定]** 登出、改密、密码重置和停用必须使旧会话在服务端失效。
- **[接口约定]** 每次受保护请求都检查账号当前状态，不能只在登录时检查。

### 2.2 身份与权限

- **[接口约定]** 替换 `app/auth_contract.py` 中开发用的 `X-Role`、`X-Subject-ID` 身份来源；生产路径必须从验证过的会话识别用户。
- **[接口约定]** 保持 `CurrentUser(role, subject_id)` 结构和含义不变。
- **[接口约定]** 角色统一使用 `student`、`teacher`、`registrar`；前端的 `admin` 不能直接成为后端授权角色。
- **[接口约定]** 学生业务从 `CurrentUser.subject_id` 取得当前学生 ID，不相信请求体自报的学生 ID。
- **[需求-已确认]** 学生只能操作自己的方案并查看自己的成绩；教师只能管理自己负责的授课和成绩；师生资料仅由教务维护。
- **[核心设计]** 成员 3 负责认证和角色检查。方案归属由成员 1 检查；教师与班次、成绩的归属由成员 4 检查。

### 2.3 师生资料管理

| 资料 | 必需字段                                                                                 |
| ---- | ---------------------------------------------------------------------------------------- |
| 学生 | **[需求-材料]** 姓名、出生日期、社会保障号码、状态、毕业日期；另有系统分配的学号。 |
| 教师 | **[需求-材料]** 姓名、出生日期、社会保障号码、状态、院系；另有系统分配的教师编号。 |

- **[需求-授权决定]** 演示使用虚构的社会保障号码，不替换为真实身份证号。
- **[需求-授权决定]** 日期必须有效，出生日期不能晚于当前日期；状态使用固定枚举。
- **[需求-已确认]** 教务可以新增、查询和修改师生资料。
- **[需求-已确认]** 没有业务记录的人员和账号可以删除；已有业务记录时只能停用并保留历史关联。
- **[需求-授权决定]** 停用不自动退课、不取消授课、不删除成绩或账单。
